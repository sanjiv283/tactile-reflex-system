# Design and Simulation-Based Evaluation of a Tactile Reflex Controller with Force-Limit Enforcement and Fault Handling

*Status: complete DRAFT for the author's review. Everything reported is from simulation, formal proofs of two modules and software tests; **no physical hardware, Quartus build or Wokwi run was performed**. Numbers come from the files named in each section and regenerate with the commands in Section 8. Items marked **[TODO]** are not done or not verified.*

## Abstract
We describe a deterministic tactile reflex controller for a robotic gripper and evaluate it without hardware. The design (FPGA RTL, AD7476A-class SPI ADC input, PWM output intended for a DRV8871 H-bridge) enforces a force limit with hysteresis, a slope-based predictive pre-limit, a latched e-stop, and sensor-fault handling that forces the drive inhibited. Fifteen scripted scenarios (159 checks) were run through (a) a small software model of the documented behaviour and (b) the real RTL under Icarus Verilog on identical stimulus, and compared with a threshold-only baseline. The model met 159/159 checks and the RTL 157/159; the two RTL misses arise because the step-level stimulus for S06a, intended as one invalid sample, lasted about 240 ADC frames in the RTL (Section 6.3). The baseline met 93/159 by design. A frame-granular comparison (577 frames) and an expansion of every step into 240 model samples (839 steps) showed no model-RTL differences. On a ramp the predictive pre-limit tripped 12 stimulus steps (6 ms of stimulus time) before the hard limit in both model and RTL. In single trials the RTL asserted `safe_state` 101-189 clock cycles (2.0-3.8 us at 50 MHz) after a force-limit stimulus; these are single-trial values, not bounds. The verification of the RTL itself was strengthened: a 19-testbench regression (4,640 assertions, of which 688 are directed and 3,952 are per-vector replay evaluations), a 49-mutant mutation campaign in which every mutant is detected, a cycle-accurate safety-invariant monitor, formal proofs of fifteen governor properties and six PWM properties for every state of those two modules (the slope predictor is not covered), a clock-domain check that follows every boundary input, and a host-in-the-loop co-simulation against an independent reference model. The new tests exposed and led to the repair of a real receiver weakness (spurious bytes after a break) and a simulation gap in the PWM period-boundary behaviour. One open hardware issue is reported openly: the input synchroniser added to the ADC data line leaves the first data bit a sampling window of only 20 ns in simulation, and the real ADC's timing is unverified (Section 6.4). The sensing and ML data are simulated and the controller has never run on a board, so no real-world safety claim is made.

**Keywords:** tactile sensing, force limiting, reflex control, FPGA, fault handling, simulation-based verification, mutation testing

## 1. Introduction and research question
Grippers must stop driving when contact force exceeds a limit even if higher-level software is slow or wrong. Question: *in simulation, does a hardware reflex path with hysteresis, slope prediction, a latched e-stop and sensor-fault inhibit behave as specified at, just below and just above its thresholds, and how does it differ from a threshold-only controller on identical inputs?* Tactile sensing for robot grasping is an established topic [1, 2], and reacting to detected contact so as to limit contact force has been studied for physical human–robot interaction [3, 4]. We make no novelty claim; a systematic literature search for prior art was not performed **[TODO]**.

## 3. System architecture
Signal path in `rtl/`: `adc_interface` (16-SCLK AD7476A-style frame, 12-bit sample) → `input_conditioning` (invalid if frame error or code ≥ 0xFF0) → `force_lut` (256-entry duty table indexed by `code[11:4]`) → `safety_governor` → `pwm_generator` (12.2 kHz, killed by `safe_state`); `fault_handler` latches e-stop and sensor faults. Top module: `tactile_reflex_top` (board wrapper `de2_115_top`). An advisory AI path exists in the RTL but is tied off in all experiments here.

Force is the raw 12-bit ADC code; the RTL contains no conversion to newtons, so all thresholds are in ADC counts. Defaults: `FORCE_MAX`=2560 (0xA00), `FORCE_REL`=2304 (0x900), `PRED_K`=2, `PRED_MIN_DELTA`=150, 3 ms prediction window (150000 clk at 50 MHz), `INVALID_LIMIT`=4, watchdog 2000 clk. `trip` = force-over (latched with hysteresis) | sensor fault | e-stop | invalid ADC | not yet armed | predicted over-force, where predicted = `delta ≥ 150 && force + 2·delta ≥ FORCE_MAX`. The DRV8871 is external: the RTL only exposes `PWM_OUT` held low in safe state; no driver-pin behaviour was simulated.

## 4. Methodology
Three artefacts, kept separate:
1. **RTL regression:** `sim/run_all.sh` runs `tools/run_regression.py` over 18 testbenches listed in `sim/testbenches.txt` (Section 5.4).
2. **Software model** (`experiments/wokwi/reflex_model.h`): C re-implementation of the documented rules, one call per ADC sample slot (500 µs of simulated time), thresholds taken from the RTL defaults, LUT generated from `rtl/force_lut.mem`. It is **not** the RTL and shares no code with it. It is intended to run on an ESP32 in Wokwi (**not yet run there**, Section 8).
3. **RTL replay** (`experiments/rtl/tb_experiments.v`): the model's per-step stimulus is replayed on the real `tactile_reflex_top` (25000 clk per step), outputs logged at the end of each step; plus `tb_single_invalid.v` (exactly one corrupted ADC frame).

**Baseline (defined before measurement):** inhibit iff the latest sample ≥ `FORCE_MAX`; no hysteresis, latch, prediction, fault or e-stop handling, no wait-after-reset. Its misses on e-stop/fault checks are therefore designed, not discovered.

**Scenarios (fixed list, none dropped):** S01 normal; S02 slow crossing; S03a–d holds at 2558/2559/2560/2561; S03e jump 2000→2559; S04 hysteresis (2304 vs 2303); S05 e-stop/latch/clear; S06a–d single invalid sample, 4 consecutive invalid, sample dropout, railed code 4095; S07 noisy crossing (±8 counts, fixed LFSR); S08 fast ramp. Expectations were written from the documented rules in `scenarios.h`. Boundary holds are approached from 60 counts below so the predictor (rise ≥150/window) is not the trip cause.

Key observations (all measured):
- **Boundary:** 2558 and 2559 do not trip; 2560 and 2561 trip on the first sample, in model and RTL. Hysteresis: after tripping, 2304 stays inhibited and 2303 releases, in model and RTL.
- **Predictor side effect (S03e):** a single jump 2000→2559, below the limit, tripped the predictor transiently (first inhibit at step 3 of the stimulus) in both model and RTL, then released. Designed behaviour, but it is a nuisance trip.
- **Noisy crossing (S07):** model and RTL inhibited once; the baseline toggled 7 times (chatter without hysteresis).
- **Fast ramp (S08):** trip at force code 2015 (trip reason = predicted) versus the hard limit reached at code 2569, i.e. 12 stimulus steps of 500 µs (300,000 clocks, 6.0 ms at 50 MHz) earlier; RTL matched step-for-step. This is a stimulus-dependent lead, not a response latency.
- **E-stop (S05):** inhibit on the press step, stays inhibited after release, resumes only after operator clear (model and RTL). The existing regression separately reports e-stop→PWM-low = 5 clock cycles (`results/sim_log.txt`, reproduced).
- **Latency.** Values are listed in the table below with their start and end events; model sample slots are never mixed with RTL clocks. The model has no ADC or pipeline delay, so its latency is 0 slots by construction and is not reported as a result. No Wokwi/MCU timing was measured **[TODO]**.
- **True single invalid frame (`rtl_single_invalid.txt`, and frame-level patterns `ferr_001`, `rail_001`):** `safe_state` asserted for 104 cycles (one frame), trip bit 3 only, no latched sensor fault, then released.

### 5.2 Frame-granular validation (`experiments/validation/`)
One model step is one ADC sample, but one 500 µs RTL step contains about 240 ADC frames (240–241 `sample_valid` pulses per 25000 clocks, measured). To test the granularity explanation directly: (a) each of 9 patterns (1, 2, 3, 4, 5, 20 and 240 invalid frames; 1 and 4 railed frames) was applied one stimulus word per ADC frame to both the RTL and the model, 577 frame-by-frame comparisons of `safe_state`, command, trip bits, sensor-fault and e-stop flags: 0 differences; (b) every original step was expanded into 240 model samples and the model's end-of-step output compared with the existing step-level RTL log: 0 differences in 839 steps. In both RTL and model one invalid frame inhibits for one frame without a latched fault, and the sensor fault latches on the 4th consecutive invalid frame. For (b) the window counter of the model copy used for validation was widened (the original `uint8_t` cannot hold a 1442-frame window); an earlier run before that fix reported 30 spurious predictor mismatches, which were traced to this setup error and are not RTL differences. Both checks regenerate byte-identically from the saved sources (`experiments/validation/run_validation_v2.py`, `step_expansion_check_v2.py`; re-run on the hardened RTL by `tools/check_validation.sh`). They compare the RTL with a model written by the same author, and compare only end-of-step (b) or per-frame (a) observations of constant-code stimuli.

### 5.3 Watchdog timing (`experiments/validation/watchdog/`)
The first model counted a sensor-fault watchdog in samples (2 missing slots); the RTL's is 2000 clocks (`WD_CYCLES`), which at 104 clk per frame means 19 or more consecutive missing frames. Frame-granular dropout runs (10 dropout lengths, 1-40 frames) showed the sample-based model differing persistently from the RTL for dropouts of 2-18 frames. The model was therefore changed (with the author's approval, patch `experiments/validation/watchdog/proposed_time_based_watchdog.diff`) to a time-based watchdog (`WD_CLK`=2000, `FRAME_CLK`=104, `SLOT_CLK`=25000 clocks). With it, the model and the RTL differ in 0 of the frames of all 10 dropout lengths (`time_based_watchdog_evaluation.md`), the step-level S06c mismatch disappears (1/40 -> 0/40) and the total goes from 14/839 to 13/839. The original model is preserved (`experiments/wokwi_v1_wd2/`) and reproduces the earlier outputs byte for byte (`experiments/validation/results_v2/OLD_VS_NEW.md`). The change makes the model follow the RTL's documented 2000-clock rule; it does not make the model an independent oracle, because it was adjusted after observing the RTL.

### 5.4 Verification of the RTL beyond the scenarios
All items regenerate with `sh sim/run_all.sh` (Section 8). Counts are from `results/regression_summary.json`, `results/mutation_report.json`, `results/mutation_audit.json`.
* **Regression.** `tools/run_regression.py` compiles and runs each testbench from `sim/testbenches.txt`, and fails unless there is exactly one summary line, no failed or vacuous assertion, no compiler warning and a clean exit. Its own behaviour is tested with deliberately broken testbenches (`tests/test_regression_runner.py`). Result: 19/19 testbenches, 4,640 assertions, 0 failures. The total is **not** a coverage measure: 3,952 of the assertions are per-vector invariant evaluations in the two replay testbenches; 688 are directed assertions.
* **A receiver weakness found and fixed.** A new UART framing testbench (49 stimulus vectors, 45 assertions: bad stop bit, break, glitches, 7/9-bit and truncated frames, reset mid-frame) showed that `uart_rx` could emit spurious bytes after a break or framing error, and that the two-flop input synchroniser's reset value makes a line held low across a reset release look like a fresh start bit. The receiver now waits for four consecutive idle clocks before re-arming. This is a change to the RTL made because of verification, not a property of the original design.
* **Reset and key handling.** A reset synchroniser (asynchronous assert, synchronous release), a debounced edge-triggered fault-clear key (one event per deliberate press; a key held through reset or held while the e-stop is released does not clear), a synchroniser on the ADC data input, and an undebounced e-stop path were added and tested at module level and at board-wrapper level, including a 3 ns reset pulse, a half-received AI packet cut by such a pulse, and the two-clock reset release. The simulated debounce time is 32 clocks; the board value is 1,000,000 (20 ms) and was not simulated at that value.
* **Mutation testing.** `tools/mutation_test.py` applies 49 hand-written single-edit faults (threshold, hysteresis, trip causes, AI limits, PWM kill and period boundary, UART, synchronisers, key logic) to a temporary copy of the RTL and runs the whole regression. All 49 are detected. `tools/mutation_audit.py` confirms that each edit is applied once in the intended file, each mutant compiles, and each is detected by a failed assertion rather than by a warning or timeout, and enforces robustness targets for six mutants whose kills had rested on a single assertion. Campaign findings so far: an invalid mutant after an RTL edit, a mutant killed only by a timeout, a survivor that exposed a missing wrapper-reset test, and **M48 (PWM loads the duty every clock) which survived all simulations until an exact period-boundary assertion was added**. A full score on hand-written mutants measures sensitivity to those faults only.
* **Safety-invariant monitor.** `tb/safety_monitor.v` checks six invariants on every clock in five system-level testbenches and in the co-simulation (safe state carries zero command; PWM low one clock after safe state; fault causes and the force limit force the safe state; the command never exceeds the LUT command; reset forces the safe state). It reports no violation on the RTL and flags each of the six safety-specific mutants.
* **Formal proofs (Yosys `sat`, no `sby`).** `formal/pwm_props.v` (W1 to W6) and `formal/gov_props.v` (P1 to P15) are one-step relations of the transition functions of `pwm_generator` and `safety_governor`, checked from a free initial state: no counterexample means each holds in every state the module can reach, for all inputs, including every counter value of the 4,096-clock PWM period. They cover the PWM kill and period-boundary behaviour, the force limit and its hysteresis latch, arming, the trip causes, the exact AI caps and the override flag. Run against every governor/PWM mutant, the check refutes 19 of 21; the two it does not are the slope-predictor mutants, which are **not established formally**. An earlier bounded check (14 clocks from reset) was vacuous for the PWM kill, because the PWM loads a new duty only at the counter wrap, and was replaced. These are proofs about two modules as written; nothing is claimed about the other modules, timing or hardware.
* **Structural clock-domain check and lint.** `tools/cdc_check.py` follows every input bit of the two boundary modules through the hierarchy and requires each use to be a recognised synchroniser (11 negative tests, including a newly added unsynchronised input); `tools/lint_synth.sh` runs Yosys checks (no latches, no combinational loops) and a generic LUT4 mapping (about 625 LUT4 and 466 flip-flops; not a Quartus fit, no timing).
* **Host-in-the-loop co-simulation.** `tools/cosim_host_rtl.py` runs the real host code against the real board RTL over a 52-step trace (ramp, hysteresis band, fast jump, e-stop at mid and over-limit force, ADC frame errors with latching, operator clears) in six passes: no AI, the real model, two hostile constant AIs, a host that dies, and a corrupted link (bad checksum, wrong header, garbage, inconsistent class bits). An independent reference model predicts the safe state, latches, command, AI validity and class; on 120 settled frames per pass the RTL and the telemetry decoded by the host parser equal the prediction, with minimum coverage counts asserted. It detects 11 of 11 injected faults. It is open loop (the host's answers do not feed back into the ADC trace) and uses an ideal UART and a behavioural ADC.
* **Host and ML software.** The laptop-side program was rewritten around a testable session class and a resynchronising parser (25 unit tests with a mock serial port, plus tests of the model format, the real-data pipeline, calibration, pin checking, Quartus project generation, ADC timing and the co-simulation: 74 Python tests in all), a host-to-RTL packet test (`tb_host_link`, 48 packet groups), and a JSON decision-tree format replacing a pickled model (identical predictions to scikit-learn on 240,000 simulated samples). Validation on the simulated dataset: grouped 5-fold accuracy 0.926 +/- 0.008 (force-only baseline 0.862); label-shuffle control at the majority rate; excessive-force recall 0.72 (`results/ml_validation.json`). The AI path is advisory and can only lower the command; its accuracy is not a safety property.

## 6. Discussion and threats to validity
### 6.1 What the evidence supports
Within these scenarios, the RTL and an independent re-implementation of its documented rules agree on inhibit/command/trip-reason at the end of every 500 µs step in 826 of 839 comparisons; the remaining 13 are all in the S06 fault scenarios and are explained in Section 6.3 and verified by Section 5.2 (0 differences once the model is fed at the RTL's sample granularity). Watchdog dropout timing agrees once the model uses the same time-based rule (Section 5.3).
### 6.2 What it does not support
Neither source proves physical safety. Inputs are synthetic code sequences, not FSR measurements; the ADC is a behavioural model; no DRV8871, motor, mechanics or EMI were simulated; thresholds are untuned defaults with no unit conversion; 15 scenarios is not coverage. Model–RTL agreement does not establish equivalence: the model was written by the same author from the same source, so a shared misreading would go undetected. Baseline comparisons are against a deliberately weak controller. The frame-level patterns use constant codes (no slope-dependent timing), nine fault patterns only, and the same tools (iverilog 12.0, gcc) on one machine; reproducibility was shown by regeneration, not by independent replication. Model sample timing (500 µs slot, 1 ms watchdog) is a modelling choice, not RTL timing.
### 6.3 Disagreements
The model counts *samples* (one step = one sample); the RTL counts *clocks* (one 500 µs step ≈ 240 ADC frames). Hence S06a, intended as a single invalid sample, became an ≈240-frame invalid burst in the RTL, which latches a sensor fault (correctly, per `INVALID_LIMIT`=4); this accounts for its 2 RTL check misses and 7 differing steps. The scenario ID is kept in the evidence files, but it should be described as an invalid burst; the single-frame case is covered by the frame-level patterns and `rtl_single_invalid.txt`. S06b and S06d differ only in the RTL asserting the latched-fault bit earlier within the same step; All 13 differences disappear when the model is fed 240 samples per step (Section 5.2).
### 6.4 Limits of the verification evidence
Mutation score, the monitor, the formal proofs and the co-simulation are statements about this RTL in simulation. They do not cover: real ADC and driver behaviour, timing closure on the FPGA (no Quartus run; Yosys numbers are generic), metastability (checked structurally only), the board-level debounce time, power-up pin states before configuration, a hung or clock-less FPGA, or the fact that the e-stop acts only through the FPGA (`HAZARD_ANALYSIS.md`, `docs/DRV8871_SAFE_STATE_ANALYSIS.md`). The pin assignments in `constraints/de2_115.qsf` are **not verified** and 24 of 41 port bits are unassigned; `tools/check_pins.py` will verify them against Terasic's file once supplied **[TODO]**.

**Open ADC timing hazard (H-16).** The two-flop synchroniser added to the ADC data line delays the data by two clocks. Each data bit is therefore sampled 4 clocks (80 ns) after the ADC launches it instead of 6 (120 ns), and the first bit, which carries the frame-error indication, only 1 clock (20 ns) after chip-select falls instead of 3 (60 ns). Against an idealised ADC model with a programmable output delay (`tools/adc_timing_sweep.py`, pinned by `tests/test_adc_timing.py`), the testbench passes up to a 20 ns delay with the synchroniser (fails from 22 ns) and up to 60 ns without it (fails from 62 ns). These are the RTL's own sampling windows against an ideal delay. They are **not** a hardware margin: the real AD7476A output delay and the board delays are unverified, the 60 ns figure is not evidence that the original wiring is safe, and no timing guarantee is claimed. A mis-sampled first bit makes a healthy frame look invalid (fail-safe, availability) or hides a leading-1 error. The hazard remains an unresolved hardware blocker and the decision on the structure is pending.

The hazard analysis lists 16 hazards of which several remain open.

## 7. Conclusion and future work
Without hardware, the controller behaves as documented at the force boundary, through hysteresis, under e-stop, under sensor faults and across resets, and the predictive pre-limit trips earlier on fast ramps at the cost of nuisance trips on large jumps. The strengthened test set found and led to one real RTL repair and two test gaps (wrapper reset, PWM period boundary), all closed; it also exposed an open ADC timing hazard (H-16) that is not resolved. Everything above is simulation. Future work, in order of value: (0) decide the ADC data-line structure after measuring the real part (H-16); (1) obtain Terasic's pin file, verify the pin assignments, build with Quartus and read the timing report; (2) calibrate the force thresholds with a real sensor using `tools/calibrate.py`; (3) add a hardware e-stop path independent of the FPGA and resolve configuration-time and stuck-PWM behaviour (`docs/DRV8871_SAFE_STATE_ANALYSIS.md`); (4) run the Wokwi build; (5) replace the synthetic ML data with recorded sessions through `ml/real_data_pipeline.py`; (6) bench tests with a current-limited driver and no mechanical load under appropriate supervision.

```bash
sh sim/run_all.sh                       # LUT, ML, CDC check, formal proofs, lint/synth, unit tests, ADC timing sweep, 19-testbench regression
python3 tools/check_artifacts.py        # derived artifacts regenerate byte-identically (temporary copy)
sh tools/check_experiments.sh && sh tools/check_validation.sh    # scenario and frame-level comparisons on the current RTL (about 5 min)
python3 tools/mutation_test.py --jobs 4 && python3 tools/mutation_audit.py   # 49-mutant campaign and its audit (about 20 min each); then: python3 tools/cosim_negative_controls.py
python3 tools/check_traceability.py     # every item cited in HAZARD_ANALYSIS.md exists
```
