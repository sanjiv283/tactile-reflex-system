# Hazard analysis and requirements traceability

**Scope:** the tactile reflex controller (FPGA RTL, host software, driver interface) as built in this repository.
**Evidence level:** simulation, formal proofs of the governor and PWM transition functions (see section 4) and software tests. **No hardware has been run**, so no hazard is closed at the system level.
This is an engineering analysis, not a certified safety case (no IEC 61508 / ISO 13849 claim is made).
References such as `tb_top`, `M13`, `S2`, `P4` are machine-checked by `tools/check_traceability.py` (every cited testbench, mutant, monitor invariant and
formal property must exist, and every cited mutant must be KILLED in `results/mutation_report.json`).

Status vocabulary: **SIM** = demonstrated in RTL simulation; **PROVEN** = formally proven for every state and input of the named modules (one-step transition properties, `tools/formal_check.py`; a proof about those modules only, not about timing or hardware); **BOUNDED** = checked only to a depth (none is claimed at present); **OPEN** = not mitigated or not verified;
**BLOCKED** = needs hardware, a licence-bound tool, or a document that could not be obtained.

Effect of a mis-sampled first bit: a healthy frame looks invalid (fail-safe, availability loss) or a leading-1 error is missed (the three `tb_top` frame-error checks fail). ## 3. Formal verification status (`tools/formal_check.py`, `results/formal_report.json`)

How it works: each property in `formal/pwm_props.v` (W1 to W6) and `formal/gov_props.v` (P1 to P15) is a one-step relation of the transition function. It is checked with Yosys `sat` **from a free initial state** (every register arbitrary, inputs free every clock), on instrumented copies of `pwm_generator` and `safety_governor` that only add output ports. No counterexample from every state means the property holds in every state the module can ever be in, so for the PWM it covers every counter value of the 4,096-clock period (an earlier reset-anchored 14-clock check was vacuous for the kill, because the PWM loads a new duty only at the counter wrap; that check has been replaced).

| Class | Content |
|---|---|
| **PROVEN** (for every state and input of `safety_governor` + `pwm_generator`) | W1 kill forces the PWM output low on the next clock; W2 reset clears output, duty and counter; W3 counter +1 per clock (period exactly 4,096); W4 active duty changes only at the period boundary, then to the commanded duty; W5 output = compare(counter, active duty) unless killed; W6 zero duty never gives a pulse. P1 safe state carries zero command; P2 PWM low after safe state (through the real PWM stage); P3 e-stop / sensor fault / invalid ADC force the safe state; P4 valid force at or above the limit forces it; P5 command never above the LUT command; P6 reset forces it; P7/P8 override flag and AI-used flag exact; P9/P10 AI class 2 / 3 caps (64 / 24); P11/P12 arming; P13 force latch with hysteresis; P14 latch forces the safe state; P15 (predictor off) safe state for exactly the documented causes |
| **BOUNDED** | none claimed |
| **NOT ESTABLISHED** | the slope predictor (M07 and M12 are the only governor/PWM mutants the formal check does not refute; covered by simulation and the 4,720-vector reference comparison), the LUT, `fault_handler` (watchdog, latches, clear), `button_debounce`, `reset_sync`, UART, `ai_control_interface` timeout/integrity, host, any multi-clock liveness ("eventually"), timing, analogue and physical behaviour |

Negative controls: the same check is run against every governor/PWM mutant (`results/formal_report.json`): **19 of 21 refuted**, including M13/M42 (PWM kill removed), M48 (duty loaded every clock) and M49 (compare `<=`), M02 (no hysteresis), M06 (no arming), M08/M09 (AI caps) and M11 (override flag). This is a proof about those two modules as written; it does not prove the requirements are the right ones.

## 4. What this analysis does not cover

Mechanical hazards (pinch points, gearbox self-locking), electrical safety of the 12 V supply, EMC, thermal behaviour of the motor/driver, human-factors of the
e-stop placement, long-term sensor drift, and failures of the FPGA device itself. These need a system-level review with the real hardware.
